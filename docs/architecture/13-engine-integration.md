## 1. Relationship to UzEngine

- UzPainter **copies (vendors)** from UzEngine the minimal rendering code it needs and nothing else. There is no link against `runtime.lib`, no DLL, no submodule, no pin that must be kept current, no patch queue and no obligation to upstream changes. After the copy the two code bases evolve independently.
- The copy is taken from a **clean commit** of UzEngine (§3.1). The commit hash is recorded for attribution and provenance only; it is not a dependency pin.
- The copy is treated as third-party Apache-2.0 code although both projects belong to UzmiGames, because UzEngine is released separately and may contain contributions under its licence. Licence handling, attribution, manifest and modification log: §3.3.
- Known defects are fixed in the copy or the affected path is not taken (§2.4, §3.4). In particular the glTF 32/48-byte stride defect is avoided: none of the files involved is vendored.
- **Future direction (not now):** UzEngine may later consume UzPainter as a submodule. Nothing is built for that today. The constraint kept now is isolation: UzPainter's own code never includes a path into a UzEngine checkout, and the vendored copy lives under one folder (§3.2), so a future consumer can supply its own originals or keep the copy behind a boundary. How symbol collisions would be avoided (namespace or DLL boundary) is decided when the owner requests that integration.

## 3. Vendoring procedure (P0-VENDOR)

### 3.1 Commit selection

1. The source is a **commit object** on UzEngine's `main` branch, identified by its full hash. Files are exported from that commit (for example `git archive <hash>` into a staging folder outside both repositories), never copied from a working tree. This excludes the mid-merge tree of 2026-10-10 and any checkout with uncommitted edits.
2. The candidate must pass all of these checks: (a) no conflict markers in any file of the manifest; (b) the include closure computed from the exported tree equals the manifest, with no unresolved include outside the listed third-party and system headers; (c) UzPainter's build of the subset and the hardware slice of `UzPainter.exe selftest` pass (§4.2); (d) every behaviour cited in §2.3 and §3.4 is re-verified at that commit. UzEngine's own build and test status at that commit is recorded as information only; it is not a UzPainter gate.
3. Among candidates that pass, take the newest commit on `main` at the time of P0-VENDOR.
4. State on 2026-10-10, read from the checkout's files: the PR #10 merge (`9220973`) that was in progress during the analyses has since been committed (`77b8381`, followed by commits up to `380c142`), and the checkout carries uncommitted edits. The analyses' baseline `19ffb9b` predates that merge, and the merge changed RHI files (for example the DX12 3D-texture readback path). These facts do not select the commit; the checks do.

### 3.2 Layout

```
thirdparty/uzengine-render-core/
  LICENSE            UzEngine's LICENSE at the selected commit (Apache-2.0, "Copyright 2026 Uzmi Games")
  ORIGIN.md          repository, commit hash and date, selection evidence (§3.1), import date, importer, re-verified line numbers
  MANIFEST.json      one entry per vendored file (§3.3)
  MODIFICATIONS.md   local modifications log (§3.3, §3.4)
  engine/…           files at their upstream paths relative to UzEngine runtime/
  platform/…
thirdparty/<library>/  each third-party library from its own upstream, with its LICENSE/NOTICE files and an ORIGIN.md
```

Upstream relative paths are kept so that includes resolve unchanged and every manifest entry maps one-to-one to an upstream file.

### 3.3 Licence, attribution, manifest and modification log

- **Headers.** UzEngine's source files carry **no per-file licence or copyright header** (none of the files under `runtime/engine` or `runtime/platform` contained one on 2026-10-10); the Apache-2.0 grant and the copyright line are in `LICENSE`. Unmodified files are therefore copied byte for byte, which keeps their hashes equal to upstream, and the licence travels as `thirdparty/uzengine-render-core/LICENSE`. If the selected commit adds per-file headers, they are kept verbatim (Apache-2.0 §4(c)).
- **Modified files** carry a prominent notice at the top (Apache-2.0 §4(b)): `Modified by UzmiGames for UzPainter — see thirdparty/uzengine-render-core/MODIFICATIONS.md <id>. Original: UzEngine runtime/<path> at <commit>. Licensed under the Apache License, Version 2.0.`
- **NOTICE.** UzEngine has no `NOTICE` file (none at the repository root, in `runtime/`, or under `runtime/engine` and `runtime/platform` on 2026-10-10), so Apache-2.0 §4(d) adds no text to propagate today. UzPainter's root `NOTICE` still names the vendored UzEngine code, its copyright line and the selected commit. P0-VENDOR re-checks for a `NOTICE` at the selected commit and, if one exists, reproduces its attribution notices (`docs/licensing-and-clean-room.md` §3).
- **Manifest** (`MANIFEST.json`): per file `{upstream_path, vendored_path, upstream_commit, upstream_blob_sha1, upstream_sha256, vendored_sha256, status: verbatim|modified, modifications: [ids]}`.
- **Modification log** (`MODIFICATIONS.md`): per change `{id (UZP-MOD-nnn), files, reason (defect | trim | platform | capability), description, upstream behaviour cited as path:line at the selected commit, date, author, covering test}`.
- **Vendoring check** (`python -m tools.vendoring.vendor_check`, in the local full gate before each push, decision 200): recomputes `vendored_sha256` and fails on drift not recorded in the log, a modified file without its notice, a file outside the manifest under the folder, a path on the denylist (`asset/importers/**`, `asset/formats/uzmesh_format.*`, `asset/formats/uztexture_format.cpp`, `renderer/**`, `engine/config/**`), conflict markers, or any include/library path in the build that points outside the UzPainter repository.

## 4. UzPainter-owned render code and build

### 4.1 UzPainter-owned code on top of the copy

`TextureReadback` (per-request ownership, aligned pitch, fence-linked map, drain) on both backends; backend selection and capability queries (formats, usages, ray queries, VRAM); the acceleration-structure builder for its own meshes; the shader-cache key; UV-space rasterisation pass; dilation/padding compute; resampling; mip generation (sRGB-aware, normal-renormalising, alpha-coverage); height→normal; compositor kernels; the `painter_viewport` forward pass; the `painter_iray` path tracer (inline ray queries on DXR 1.1 and Vulkan); the Vulkan additions of §3.4 (UZP-MOD-007); the DDS writer; the `.uztexture` and `.uzmat` writers; VRAM admission; the CPU job pool.

The render layer lives in `src/render/` (Phase 1, P1-CORE): backend-neutral interfaces (`backend.h`: device, queue, resources, compute kernels, the wait result `signaled|timeout|device_lost`, the errors `gpu_backend_unavailable`, `device_removed` and `timeout`); the DX12 device and queue over the vendored RHI (`device.*`); the engine thread, sole owner of the device, which runs requests against revision snapshots in submission order, completes them through futures and bounds every GPU wait by the request's deadline (`engine_thread.*`, default 60 s); the kernel compile path and cache (`kernel_cache.*`: HLSL to DXIL and SPIR-V through `uz::ShaderCompiler` with UZP-MOD-008, entries under `%LOCALAPPDATA%\UzPainter\kernel-cache` keyed by XXH64 over source, declared includes, defines, target, compile flags and DXC version; UzPainter implements XXH64 in `xxhash64.*`, checked against reference digests; a kernel sees only its declared includes); the capability query with the admission budget (`capabilities.*`); and `TextureReadback` (`texture_readback.*`, `phase1.2_core-readback`). A readback lives inside one engine request: each request validates the texture (live handle, `CopySrc` usage, mip and slice in range, a readable format), owns its own staging buffer (`Readback` memory, rows at the row size rounded up to a multiple of both 256 bytes and the texel size: the pitch D3D12's copy footprint reports for power-of-two texels, 768-byte steps for the 12-byte `RGB32Float`, so a row is a whole number of texels for Vulkan's `bufferRowLength`, decision 310), and submits its copy as its own submission; `Complete` maps the buffer only after the wait for that submission's fence returned `signaled` and otherwise fails with the wait's `timeout` or `device_removed` and no texels; `Drain` completes or fails every outstanding request in submission order and releases every staging buffer (one whose wait timed out is kept until its copy has completed or the device is lost, because the GPU may still write it). Texels come back tightly packed and unconverted: 8-bit and 16-bit unorm (UZP-MOD-009), 16- and 32-bit float and 32-bit uint, one to four channels; block-compressed and depth formats are rejected. Three-channel `RGB8`, `RGB16` and `RGB16F` data, which has no GPU format of its own, is held in the four-channel format of its depth and read back with three channels. The UV-space raster pass (`uv_raster.*`, kernel `shaders/uv_raster.hlsl`, `phase1.3_core-uv-raster`; `12-mesh-import.md` §5) is a compute pass inside one engine request. The image passes (`phase1.3_core-image-passes`; shared rules in `image_pass.h`, kernels in `shaders/`) are compute passes inside one engine request as well, on textures in the `Common` state, each one submission: jump-flood dilation over a coverage mask with a Euclidean distance limit (`dilation.*`; steps 1, N/2, ..., 1, ties to the smaller linear index, covered and out-of-reach texels copied bit for bit); resampling with the filter as a parameter (`resample.*`: `Nearest` and Painter's fixed-point `Bilinear` of `parity/semantics/resampling.json`, exact-area `Box`; identity size is a copy); and mip generation (`mips.*`: box levels, sRGB-aware, normal-renormalising and exact alpha-coverage-preserving modes). Their arithmetic is exact integer arithmetic on unorm codes and single IEEE float operations in a fixed order, unorm results written with the float-to-UNORM rule (truncate to n + 4 fractional bits, nearest, ties down) and 16-bit floats rounded to nearest even, so each pass equals its CPU reference (`tests/render/reference/`) bit for bit and repeats byte for byte; float32 denormal inputs may be flushed by the GPU. Native tests: `tests/render/` (`zig build render-tests`). No header of `src/render/` reaches a DX12, DXGI or Vulkan header, directly or through the vendored RHI headers (`tests/render/test_render_core_layer.py`); `device.h` names `ID3D12Device` only as a forward declaration for the DX12 implementation and its tests. The vendoring check's build-path rule covers the render-layer test target as well as `UzPainter.exe`. The P1-CORE acceptance run is `parity/reports/phase1/render-core-layer.md`.

### 4.2 Build and toolchain decision procedure

- UzPainter has its **own build** (`build.zig`): one toolchain (Zig/clang) compiles the vendored render core as a static library, the UzPainter C++ sources and the pybind11 module; CPython 3.13 is embedded through its C API. No include path, library path or build step refers to a UzEngine checkout.
- **Why Zig still fits:** UzEngine's own `build.zig` already compiles exactly these source files with Zig and its bundled libc++ (`runtime/build.zig:1-12`; at the selected commit `380c142e` the flags at `:34-35` are `-std=c++17 -DSPDLOG_COMPILED_LIB` plus the profiling defines, and `build.zig.zon` declares `minimum_zig_version = "0.14.0"`), so the vendored subset does not dictate another toolchain. UzPainter compiles it with `-std=c++23 -DSPDLOG_COMPILED_LIB` (and `-DSPDLOG_WCHAR_FILENAMES` since UZP-MOD-010), without the profiling defines, under Zig 0.15.2: the subset with UZP-MOD-001…006 compiles and links cleanly at that level (`phase0.3_vendor-modifications`, 2026-10-10).
- **Static library (as built, `phase0.3_vendor-modifications`):** `zig build render-core` produces `uzrendercore.lib` for `x86_64-windows-gnu` from the subset's translation units, spdlog's seven units and `spirv_reflect.c`. `build.zig` refuses any Zig other than 0.15.2 and `build.zig.zon` declares the same version. Include paths are the vendored folder's (`.`, `engine/{logging,assertions,profiling,math,rhi,shader,paths}`, `platform/windows`, `engine/rhi/dx12`, `engine/rhi/vulkan`) and `thirdparty/<library>/…` in the order of `tools/vendoring/thirdparty.py`; the Windows system headers and import libraries come from the MinGW-w64 files bundled with Zig, so no Windows SDK installation is read. `engine/rhi/dx12/dx12_agility.cpp`, whose `D3D12SDKVersion`/`D3D12SDKPath` exports the D3D12 loader reads from the executable only, is compiled into each executable rather than the library, as in UzEngine's build; `volk.c` is compiled through `vulkan_device.cpp`, which defines `VOLK_IMPLEMENTATION`. `zig build native-tests` builds `uzp-vendor-tests.exe` with `dxcompiler.dll`, `dxil.dll` and `D3D12\D3D12Core.dll` beside it; `tests/vendoring/test_modifications.py` builds both from a fresh cache, checks that the build log holds no path outside the repository other than the Zig toolchain's own folders, and runs the modification tests. The P0-VENDOR acceptance (`phase0.5_vendor-render-core`, `tests/vendoring/test_render_core_integration.py`) copies the package that `build.zig.zon` declares (`.paths`) to a folder outside the repository, builds both steps there with empty local and global Zig caches, and checks from Zig's cache manifests that every file read, every included header among them, lies in the copy or in Zig's own `lib` folder; it also checks that the repository holds no `.gitmodules`, `runtime.lib` or patch queue, that `build.zig.zon` declares no package dependency, and that `build.zig` names files only through `b.path`.
- **Executable and `selftest` (as built, `phase0.6_toolchain-hardware-slice`):** `zig build painter` builds `UzPainter.exe` from `src/` (`main.cpp`, `selftest/`), `dx12_agility.cpp`, zlib's and spng's C sources and `uzrendercore.lib`, with libc++ linked statically, and installs it with `dxcompiler.dll`, `dxil.dll`, `D3D12\D3D12Core.dll`, `embree4.dll` and `tbb12.dll` beside it; the vendoring check builds this step too. `UzPainter.exe selftest [--out-dir <dir>] [--report <file>] [--no-gpu]` runs ordered stages (`src/selftest/harness.h`: name, mandatory, needs GPU, dependencies; later stages are added through `Selftest::Add`), prints `PASS`/`FAIL`/`SKIP` per stage, writes a JSON report (`uzpainter.selftest/1`: environment with OS build and Zig version, per-stage status, reason, duration and facts) and exits 1 when a mandatory stage fails, 2 on a usage error. The hardware slice is five mandatory stages: `dx12-device` (fails before device creation when `D3D12\D3D12Core.dll` is missing, then checks that the adapter is hardware and that the loaded `D3D12Core.dll` is the one in `D3D12\`), `shader-compile` (one HLSL kernel to DXIL and SPIR-V through the vendored `ShaderCompiler`), `compute-readback` (the DXIL kernel writes a 16-bit pattern into an R16_FLOAT texture; `CopyTextureToBuffer` with a 256-byte row pitch, fence wait with a 10 s deadline, mapped readback compared bit for bit), `png16` (spng writes the pattern as a 16-bit grayscale PNG and decodes it back) and `embree` (`embree4.dll` loaded at run time, one hit with distance and barycentrics checked, one miss). With `--no-gpu` or `UZP_NO_GPU=1` (a machine without a GPU; the hosted CI until decision 200) the two GPU stages are skipped with that reason and the other three run. `tools.toolchain.link_map` produces the linker's map (Zig has no map option: the build's own `lld-link` command is rerun with `/MAP`) and checks that `uzrendercore.lib` and libc++ contribute objects; `tools.toolchain.dll_closure` measures the import closure of §5. Run on the owner's machine: `parity/reports/phase0/toolchain-hardware-slice.md` (`python -m tools.toolchain.slice_report`).
- **Probes (as built, `phase0.7_toolchain-probes`):** after the hardware slice `selftest` runs four probe stages (`src/selftest/probes.h`), none mandatory and none part of the hardware slice, all skipped with the reason under `--no-gpu`/`UZP_NO_GPU=1`. Each writes a probe report into the report's `probes` array (`src/selftest/probe_report.h`: probe, backend, adapter, driver, `completed`, `qualified`, verdict, error, supported items, executed checks with results, unsupported items with reasons, facts, devices) and its stage passes when the probe completed, whatever it found; a probe that cannot complete is `probe not completed` with its error. `dx12-ray-query` reads `RaytracingTier` and the highest shader model of the hardware device and decides through the vendored `DX12SupportsInlineRayQuery` (UZP-MOD-004), naming DXR Tier 1.1 or Shader Model 6.6 when missing. `vulkan-availability` loads the system `vulkan-1.dll` itself (to report the Windows error when it cannot), hands it to volk (`volkInitializeCustom`), creates a Vulkan 1.2 instance and records every physical device (API version, driver, LUID, every extension, the features below); the device judged is the one the vendored backend selects for adapter 0 (discrete first), and it is `available` when it has API 1.2 and every extension and feature the vendored device enables at `vkCreateDevice` (`VK_KHR_swapchain`, `VK_KHR_dynamic_rendering`, `VK_KHR_synchronization2`, `VK_KHR_timeline_semaphore`; timeline semaphores, descriptor indexing and its bindless features, buffer device address, dynamic rendering, synchronization2, `fillModeNonSolid`, `samplerAnisotropy`); `VK_EXT_memory_budget` is recorded as optional. An absent loader, one older than 1.2 or a failed instance is `unavailable` with that reason; no Vulkan device is created. `vulkan-ray-query` checks the three ray-query extensions and the `accelerationStructure`/`rayQuery` features on the same device. `warp` creates the vendored DX12 device on the WARP adapter (vendor 0x1414, device 0x008C) and runs the slice's compute path on it as checks `dx12-device`, `shader-compile` (the cs_6_6 DXIL, usable when WARP reaches SM 6.6), `compute-readback` and `png16`, recording WARP's capabilities; a failed check is unsupported with its reason, the checks after it are not run with theirs, and `hosted_warp_lane` lists only the checks that passed (`14-parity-testing.md` §7). `zig build probe-tests` builds `uzp-probe-tests.exe`, which runs the probe decisions on fabricated capability sources for `tests/toolchain/test_probes.py`; that test also hides the Vulkan loader from a copy of the folder (a non-DLL `vulkan-1.dll` beside the executable ends the DLL search). Run on the owner's machine: `parity/reports/phase0/toolchain-probes.md` (`python -m tools.toolchain.probes_report`).
- **Embedded CPython (as built, `phase0.7_toolchain-cpython`):** `UzPainter.exe` imports `python313.dll` of the CPython 3.13.16 embeddable package (`thirdparty/cpython/`, from python.org; headers and `python313.lib` from the same release's full Windows package, `thirdparty/cpython-dev/`) and compiles pybind11 3.1.0 (`thirdparty/pybind11/`) with the rest of `src/` under the same Zig; no separate DLL or C-ABI layer was needed. `src/python/interpreter.cpp` starts the interpreter from `PyConfig_InitIsolatedConfig` (environment variables, the user site-packages and the current folder ignored; no bytecode written into the read-only install folder: `zig build painter` compiles checked-hash `.pyc` files for `python\` and `Lib\site-packages\` with the build's Python 3.13, which the interpreter checks against each source's hash on import, decision 253), and `python313._pth` beside the DLL (`src/python/python313._pth`) sets `sys.path` to `python313.zip`, the install folder (the package's `*.pyd`), `Lib\site-packages\` and the app's own `python\` folder (the `substance_painter` facade, phase1.20), with `import site` for the `.pth` files of the wheels. `uzpainter` is a built-in module (`PYBIND11_EMBEDDED_MODULE`, `src/python/uzpainter_module.cpp`); in Phase 0 it holds only the boundary checks `uzpainter._selftest`. `zig build painter` installs the package's files, `python313._pth` and the 29 pinned wheels of the `mcp==2.3.0` closure (`thirdparty/python-wheels/`, `tools/vendoring/wheels.py`) unpacked into `Lib\site-packages\` (without console scripts, pywin32's MFC-dependent `pythonwin` and its LGPL-2.1 `adodbapi`). Five mandatory, non-GPU stages follow the probes (`src/selftest/cpython_stages.h`): `cpython-start` (release 3.13.16 from the folder's `python313.dll`; isolated flags; every `sys.path` entry and every loaded module inside the install folder, the app's `python\` folder included), `cpython-uzpainter` (built-in, no file), `cpython-buffer16` (0…65535 from a C++ buffer to a Python `array('H')` through the buffer protocol and back, compared byte for byte in C++ and value by value in Python and in a bound function), `cpython-exceptions` (Python `ValueError` and a script-defined `RuntimeError` subclass caught in C++ as `error_already_set` with type and message; `std::invalid_argument`, `std::out_of_range`, `std::runtime_error` and a registered C++ exception arriving in Python as `ValueError`, `IndexError`, `RuntimeError` and `uzpainter._selftest.BoundaryError` with their messages; the interpreter usable afterwards) and `cpython-mcp-sdk` (the SDK and the native modules of pydantic-core, rpds-py, cffi, cryptography and pywin32 imported from `Lib\site-packages\`; an in-process MCP client lists and calls a tool of an `MCPServer`). `UzPainter.exe` has no `longPathAware` manifest, so the install folder path is limited to 161 characters (the deepest installed file is 97 characters below it; a deeper folder leaves wheel files unreachable under `MAX_PATH`). Run on the owner's machine: `parity/reports/phase0/toolchain-cpython.md` (`python -m tools.toolchain.cpython_report`); route: direct.
- **Decision procedure:** (1) pin the Zig release (0.15.2) in `build.zig.zon` and `build.zig` (the hosted CI that also pinned it was removed, decision 200); (2) P0-TOOLCHAIN runs the selftest below; Zig stays if the hardware slice passes; (3) if only the CPython/pybind11 boundary fails, apply the fallback (the Python-facing layer as a separate DLL with a C ABI to the core) and rerun, still under Zig; (4) the toolchain changes (clang-cl or MSVC with a UzPainter-owned CMake build) only on recorded evidence that (a) a vendored file cannot compile or link under the pinned Zig without changes beyond the modification log, (b) the CPython boundary fails both directly and through the C-ABI fallback, or (c) a required prebuilt binary (`python313.dll`, `embree4.dll`, `dxcompiler.dll`, `D3D12Core.dll`) cannot be loaded or used from a Zig-built executable. Such a change updates decision 021 with the failing selftest output; it never reintroduces a dependency on UzEngine's build.
- **Vulkan hardware slice (as built, a slice of `phase3.1_vulkan-compute-parity`, decision 310):** after the probes `selftest` runs `vulkan-device`, `vulkan-compute-readback` and `vulkan-png16` (`src/selftest/vulkan_slice.h`), reported as `vulkan_hardware_slice`, apart from the DX12 slice and the `vulkan-availability` probe; none is mandatory, so the exit code is the DX12 slice's until phase3.1's acceptance. `render::SurveyVulkan` records every physical device (identity, driver and API versions, UUIDs and LUID, every extension, features, limits, float controls, queue families, memory heaps and types, format features) from a pre-check Vulkan 1.2 instance; `render::QualifyVulkan` judges the device at adapter index 0 of the vendored order (no fallback) against named criteria (`src/render/vulkan_qualification.h`: loader and instance at least 1.2, the vendored instance and device extensions and features plus `shaderStorageImageExtendedFormats` and `shaderSignedZeroInfNanPreserveFloat32`, a hardware GPU, the first graphics queue family with compute, the update-after-bind limits of the vendored layout and pool, host-visible and device-local memory, storage-image and copy support of the kernels' formats); an unqualified device is refused before any work, naming every unmet criterion. `render::CreateQualifiedVulkanDevice` then creates the vendored device, checks its UUID, queue family and entry points, and runs three kernels (R16F pattern, R32UI hash, IEEE-strict R32F) read back bit for bit against CPU references, the pattern also against the DX12 readback. Waits are bounded; a refused or partial submission fails at once and a failed device keeps every resource; teardown destroys the device only after its last submission completed and otherwise abandons it (the vendored `vkDeviceWaitIdle` is not deadline-bounded). `render::CreateDevice` still refuses Vulkan, so no product path runs on it, and the slice is no parity evidence.
- **Phase 0 qualification slice (P0-TOOLCHAIN):** `UzPainter.exe selftest` creates the DX12 device on the hardware adapter, compiles a compute kernel from source to DXIL and to SPIR-V, writes a 16-bit PNG through readback, embeds `python313.dll`, imports the statically linked `uzpainter` module, round-trips a 16-bit buffer, raises and catches a Python exception across the boundary, imports the vendored MCP SDK wheels, runs an Embree intersection, probes Vulkan availability (a Vulkan 1.2 device, its extensions and features) and records the result, probes ray-query support (DXR Tier 1.1 + SM 6.6; Vulkan `VK_KHR_acceleration_structure`, `VK_KHR_deferred_host_operations`, `VK_KHR_ray_query`) and runs the WARP probe. **The DX12 hardware-adapter qualification slice must pass;** the Vulkan probe never fails G0, and the Vulkan hardware selftest is part of the `P3-VULKAN` gate. **The WARP probe must report supported capabilities, executed checks and explicit unsupported reasons; WARP failure leaves that software-render path unsupported and does not fail G0 unless the owner separately makes it mandatory under Q9.** "Probe completed" and "backend qualified" are reported separately.

## 6. Capacity and budgets

At startup UzPainter queries VRAM budget, descriptor capacities and format/usage support on the active backend (DX12 through DXGI memory-budget queries; Vulkan through `VK_EXT_memory_budget`, which the vendored device enables when present — `vulkan_device.cpp:455-466` — and otherwise conservatively from heap sizes) and derives the tile admission budget (`04-layer-stack-and-compositing.md` §7). The admission budget is (budget − current usage − 512 MiB reserve) × 50 %, and on DX12 live tiles are also bounded by the shader-visible descriptor capacity (less 4096 reserved, two descriptors per tile). On Vulkan no descriptor lives with a tile: every dispatch binds one snapshot of the vendored 64-binding set from one device-wide pool, so descriptors bound one dispatch's bindings (16 per type, or the device's update-after-bind limit) and the snapshots outstanding at once (128, bounded by the pool's 2048 samplers), not live tiles (`render::DeriveVulkanDescriptorModel`, decision 310). These defaults hold until P5-PERF measures the corpus. Texture-set creation above the budget fails explicitly. Peak RAM for high-poly ingestion is estimated before parsing.
