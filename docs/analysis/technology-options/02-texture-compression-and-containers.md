# GPU Texture Compression and Container Formats for Export

Research compiled 2026-10-09. Corrected 2026-10-10 after the Astra technical review (`docs/analysis/reviews/technology-options-astra-review.md`); per-finding verdicts are in `05-review-response.md`. Web sources were retrieved 2026-10-10. Sizes below are arithmetic from fixed block sizes, not benchmarks; headers are excluded.

**Fact (bit rates):** BC1 and BC4 use 8 bytes per 4×4 block (4 bits per pixel); BC2, BC3, BC5, BC6H and BC7 use 16 bytes per block (8 bpp). [Microsoft BC formats](https://learn.microsoft.com/en-us/windows/win32/direct3d11/texture-block-compression-in-direct3d-11); [BC7 format](https://learn.microsoft.com/en-us/windows/win32/direct3d11/bc7-format). UASTC LDR 4x4 is "an 8 bits/pixel LDR high quality mode"; ETC1S is "roughly .3-3bpp" (quality/content dependent). [Basis Universal](https://github.com/BinomialLLC/basis_universal)

| 4096 × 4096 texture | Base level | Full mip chain |
|---|---|---|
| BC7 / BC5 / BC6H / UASTC LDR 4x4 (8 bpp) | 16,777,216 bytes (16 MiB) | 22,369,648 bytes (≈21.33 MiB) |
| BC1 / BC4 (4 bpp) | 8,388,608 bytes (8 MiB) | ≈10.67 MiB |
| Raw RGBA8 (32 bpp) | 67,108,864 bytes (64 MiB) | ≈85.33 MiB |
| Raw R8 (8 bpp) | 16,777,216 bytes (16 MiB) | ≈21.33 MiB |

Disk size after Zstd or BasisLZ supercompression is separate from the GPU allocation of the final format.

## Container and Lossless Format Options

| Format | What It Is | Pros (Docs Export) | Cons | License | Key Source |
|--------|-----------|-------------------|------|---------|-----------|
| **DDS (DirectDraw Surface)** | Microsoft container for uncompressed or block-compressed textures: single textures, mipmaps, cube maps, volume maps and texture arrays (D3D10/11). The `DX10` extension (`DDS_HEADER_DXT10`) stores any DXGI format, including BC6H/BC7, sRGB and float formats. | Stores BC payloads with mips directly; native to DirectX tooling (DirectXTex). BC7 is 8 bpp (4096² base level 16 MiB, not 0.5 MB). | No built-in supercompression. Readers vary: Microsoft recommends the DX10 extension for formats the legacy pixel format cannot express, but "not all DDS tools support the DX10 extension". GPU support depends on format and feature level (BC6H/BC7 need Direct3D 11), and importing a DDS into an engine is not the same as uploading its blocks unchanged. "Universal engine support" is withdrawn. | **Fact**: format documented by Microsoft; implementation license depends on the library (e.g., DirectXTex MIT). | [Programming Guide for DDS](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dx-graphics-dds-pguide) |
| **KTX2 + Basis Universal** | KTX 2.0 (Khronos) is a container: `vkFormat` may be any Vulkan format — uncompressed, native block-compressed (e.g. `VK_FORMAT_BC7_UNORM_BLOCK`), or `VK_FORMAT_UNDEFINED` for Basis payloads. Supercompression (None, BasisLZ, Zstandard, ZLIB) "is applied independently to each mip level". Basis Universal is a payload choice: ETC1S (BasisLZ) or UASTC, transcoded at load to BC1–5, BC7, ASTC, ETC and others. | **Fact:** ETC1S ≈0.3–3 bpp (content/quality dependent); UASTC LDR 4x4 is 8 bpp (not 4 bpp) before optional Zstd and is designed for fast transcoding; per-mip supercompression keeps mip-level random access. | Transcode/inflate cost on load (the draft's "<50 ms for 4K" is **unconfirmed**). ETC1S loses detail on non-color data. Transcoding UASTC to BC7 does not reduce BC7 GPU memory (still 8 bpp). **Fact:** Zstd "is generally ineffective on the block-compressed data of GPU texture formats" unless the data is conditioned (e.g., RDO). Engine import varies (Unreal 5.6 import list has no KTX). | **Fact**: Basis Universal Apache-2.0. The KTX 2.0 specification carries Khronos copyright terms (no patent/trademark license granted); KTX-Software (libktx) is a separate REUSE-compliant, per-component-licensed artifact. | [KTX 2.0 spec](https://registry.khronos.org/KTX/specs/2.0/ktxspec.v2.html); [Basis Universal GitHub](https://github.com/BinomialLLC/basis_universal); [KTX-Software](https://github.com/KhronosGroup/KTX-Software) |
| **KTX2 with native BC blocks + Zstd** (added 2026-10-10) | KTX2 file whose `vkFormat` is a BC format (e.g., BC7), with optional per-mip Zstandard supercompression; no Basis transcoding. | GPU-ready blocks after inflate; mip-level random access; smaller distribution when the block stream is RDO-conditioned. | Must inflate before upload; Zstd gain on unconditioned BC data is small per the spec note above; not permitted by glTF `KHR_texture_basisu`; Unreal import unconfirmed. **Hypothesis:** suitable for UzEngine — its loader has not been checked. | **Fact**: same specification/library split as the KTX2 row. | [KTX 2.0 spec](https://registry.khronos.org/KTX/specs/2.0/ktxspec.v2.html) |
| **PNG + TIFF (Lossless)** | PNG: lossless DEFLATE for integer samples (8 or 16 bits per channel; no float). TIFF: a container with many codecs — libtiff lists None, LZW, PackBits, JPEG, Deflate, LERC and others; it is not limited to LZW/PackBits. For lossless source/interchange of integer layers. | Universal tool support; editable in image editors; lossless for supported integer samples. | PNG cannot hold float intermediates (height, displacement, HDR, bake data need EXR, float TIFF or raw typed tiles). PNG size is content-dependent; the draft's "PNG 2–4 MB vs BC7 0.5 MB / ~10×" comparison is withdrawn — BC7 4K is 16 MiB, and lossless PNG vs lossy BC7 are not equal-fidelity alternatives. | Format specifications and libraries differ; libpng/libtiff licenses were not re-verified in this pass — record the exact redistributed library and its license. | [libtiff codec coverage](https://libtiff.gitlab.io/libtiff/specification/coverage.html); [PNG Book: Compression](http://www.libpng.org/pub/png/book/chapter09.html) |
| **OpenEXR (lossless modes)** (added 2026-10-10) | Image format with HALF (16-bit float), FLOAT (32-bit float) and UINT (32-bit) channels; lossless codecs (NONE, RLE, ZIPS, ZIP, PIZ) and lossy ones (e.g., B44, DWAA/DWAB). | Holds float bakes, height and HDR intermediates losslessly in lossless modes. | Converting 32-bit working data to HALF is a quantization decision even with a lossless codec; lossy codecs must not be used for authoritative data. | **Fact**: BSD-3-Clause. [Source](https://github.com/AcademySoftwareFoundation/openexr) | [OpenEXR technical introduction](https://openexr.com/en/latest/TechnicalIntroduction.html) |
| **Channel- and precision-specific delivery formats** (added 2026-10-10) | Choose per map: BC4 (one channel, 4 bpp) for scalar masks; BC5 (two channels, 8 bpp) for tangent-space normals; BC6H (HDR half-float RGB, 8 bpp, Direct3D 11) for HDR; BC7 (LDR RGB/RGBA, 8 bpp); uncompressed R16/R16F/R32F where fidelity requires it. | Matches channel count and precision; BC4 is half the size of BC7 for a scalar map (block-size arithmetic). | BC5 normals need defined Z reconstruction, Y convention (DirectX vs OpenGL) and renormalization; per-channel error must be measured; mip generation must respect linear data, normals and masks; uncompressed float is large (R32F 4K base level 64 MiB). ## Unreal Engine 5 ORM Import Requirements

**Fact:** ORM holds numeric mask data, so it must be imported with sRGB disabled; otherwise values are gamma-decoded and the material reads wrong numbers.
- **Compression setting:** `TC_Masks` is documented as "Same compression as Default"; "Masks" does not mean BC7. `TC_BC7` is a separate setting ("High quality compressed texture, same size as BC3"). Any linear-data setting the material expects is valid; "Masks (no sRGB)" is a common choice, not an engine requirement. [TextureCompressionSettings API](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/TextureCompressionSettings)
- **Channel layout:** R=AO, G=Roughness, B=Metallic is a convention implemented by material wiring, not enforced by Unreal; a different packing is valid when the material agrees. Evaluate error per channel, not only with a perceptual RGB metric.
- **Import formats (version-dependent):** **Fact:** the UE 4.27 import guide lists `.dds` for cubemaps only; the UE 5.6 texture docs list `.dds (Cubemap or 2D)`. Neither lists KTX/KTX2. **Unconfirmed:** that pre-compressed BC7 blocks in an imported DDS survive cooking unchanged, or general KTX2 import.

**Import Path in UE5** (third-party tutorial; not verified against Epic docs): Content Browser → import texture → set Compression Settings (e.g., Masks) → confirm sRGB = false in the Details panel. Name the Unreal version and importer/plugin before promising "already compressed" exports.

Sources: [UE 5.6 textures](https://dev.epicgames.com/documentation/en-us/unreal-engine/textures-in-unreal-engine?application_version=5.6); [UE 4.27 import guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-import-guide?application_version=4.27); [third-party ORM tutorial](https://www.strayspark.studio/learn/tutorials/import-strayspark-pbr-materials-unreal-engine-5)

## glTF 2.0 Texture Format (metallicRoughness)

**Fact**: glTF 2.0 core format stores metallicRoughness as:
- **G channel**: Roughness
- **B channel**: Metallic
- **Occlusion is core, not an extension:** `material.occlusionTexture` samples the R channel and may reference the same image as `metallicRoughnessTexture` (packed ORM).

**Fact**: Core images may be external URIs, data URIs, or bufferView-backed with a `mimeType`; core MIME types are `image/png` and `image/jpeg`. A `.glb` can embed image bytes in its BIN chunk; `.gltf` + external files is the alternative packaging.

**Fact**: `KHR_texture_basisu` allows only ETC1S with BasisLZ (`supercompressionScheme` 1) or UASTC with no or Zstandard supercompression (0 or 2) — not arbitrary native-BC KTX2. A PNG/JPEG fallback can be kept in `source` unless the extension is listed in `extensionsRequired`.

**Caveat**: The extension recommends ETC1S for color data and UASTC for non-color data such as roughness-metallic and normal maps; fidelity still requires testing. Neither glTF nor GLB standardizes a Painter layer/effect project or BC7 Unreal pass-through.

[Source](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html); [KHR_texture_basisu](https://github.com/KhronosGroup/glTF/tree/main/extensions/2.0/Khronos/KHR_texture_basisu)

## Trade-Off Summary

**For UzPainter PBR Separate Maps Export:**
1. **Native engine delivery**: DDS with BC7/BC4/BC5/BC6H chosen per map for UzEngine (after its loader is checked), or lossless PNG/TGA/EXR source for Unreal import (DDS import is version-dependent; BC pass-through unconfirmed). No supercompression latency.
2. **Compact distribution**: KTX2 with native BC + optional per-mip Zstd (UzEngine **Hypothesis**), or KTX2 + Basis (ETC1S/UASTC) where a transcoder is present (glTF/web). The draft's "~50 ms load" and "50–70% disk savings vs BC7 DDS" are **unconfirmed** and withdrawn.
3. **Lossless project data (UzPainter internal)**: keep working precision — PNG for 8/16-bit integer planes, lossless EXR or raw typed tiles for float — with lossless compression. Zstd around PNG is lossless (not "near-lossless") and its gain is unconfirmed. Apply BC/Basis only to explicitly lossy caches or exports.

**Encoder Choice (for UzPainter core):**
- **CPU RDO BC7 + BC1–5**: bc7enc_rdo (MIT/Unlicense; `bc7e.ispc` Apache-2.0 only if used).
- **Windows GPU BC6H/BC7**: DirectXTex D3D11 DirectCompute (not a D3D12 path); Compressonator OpenCL/DirectX; NVTT CUDA with CPU fallback (license to be obtained). Keep a CPU path for unsupported devices and reproducibility. GPU throughput vs. contention with baking/rendering is unmeasured.
- **KTX2 writing**: Compressonator for BCn/ETCn/ASTC in KTX2 (Basis/UASTC not confirmed) or KTX-Software for Basis payloads.
- "Fastest" and "minimal dependencies" rankings from the draft are withdrawn as unmeasured; DirectXTex has no header-only option.

**Compression Quality vs Speed:**
- BC7 (+ optional RDO): fixed 8 bpp — 4096² base 16 MiB, full mip chain ≈21.33 MiB. Encode time is unmeasured (the draft's "~50–200 ms per 4K" is **unconfirmed**). RDO affects size only after a later LZ/Zstd pass.
- ETC1S (KTX2): ≈0.3–3 bpp, content dependent; artifacts on specular and other non-color maps.
- UASTC LDR 4x4 (KTX2): 8 bpp (4096² base 16 MiB before Zstd). The draft's "~100–300 MB source → 5–10 MB UASTC" and "further ~50% with Zstd" are **unconfirmed** and withdrawn.
