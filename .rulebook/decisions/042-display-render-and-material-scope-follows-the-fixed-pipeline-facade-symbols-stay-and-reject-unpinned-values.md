# 42. Display, render and material scope follows the fixed pipeline; facade symbols stay and reject unpinned values

**Status**: accepted
**Date**: 2026-10-11
**Related Tasks**: phase2.1_preview-display-presets, phase2.1_preview-viewport-window, phase3.4_path-tracer-transport, phase3.5_path-tracer-materials, phase3.6_path-tracer-tier3-report

## Context

Decision 038 limits render parity to the fixed Assets3D pipeline (standard `U-A3D-RENDERSTD-2`: the v2 common block, `presets.ref_match` v3 and the `base_color` diagnostic) and asks for the documents and tasks that assume full render-settings support to be re-scoped. Phase0.6 (`parity/reports/phase0/iray-capture-procedure.md`, decision 039) measured on Painter 12.1.5: an OCIO project raises `RuntimeError` on `display.set_tone_mapping`, and the public `display` documentation shows `get_tone_mapping` raising it too; the Python and JavaScript APIs expose only camera, environment, colour LUT and tone mapping; Save Render's PNG (16-bit) and EXR (float32) are both display-referred, so Painter has no linear output; Iray's seed is `uncontrolled`; a painted height is applied as bump. The probe's Shader Settings panel image (`probe:panel/defaults/shader-settings`, SHA-256 `9e934960aaf7b568c4163c6f97245ec7cd6af15e099ca32f11ad3c9b1288a534`) shows the default shader instance of a new project is `open-pbr` ("Main shader"): diffuse roughness off, anisotropy off, IOR 1.5, specular colour off, Transmission, Subsurface, Coat, Fuzz and Thin-film each disabled, Emission Luminance 0. The old help-page default-MDL parameters (Emissive Intensity, Refraction, Scattering, Absorption, Absorption Color) are not in it. Opacity and Displacement & Tessellation defaults were seen only in an unhashed exploration dump of a Legacy project. The Assets3D pipeline always creates OCIO projects, and its scripts call only `display.get/set_environment_resource` (plus the private `save_viewport` served by a shim). The pipeline analysis (hypothesis grade) records a shader parameter "Double sided" = true set on Tunic v10.

Model panel under the owner's delegation (cx/gpt-6-astra, kimi/kimi-k3, xai/grok-4.5, 2026-10-11):
- facade symbols stay with restricted values: AGREE x1, PARTLY x2 (record the accepted value domain, mark the preview-only domain non-parity; the getter's behaviour must rest on evidence, which the public documentation provides);
- one display configuration for preview and `painter_iray`: AGREE x3;
- display-referred outputs, linear EXR diagnostic only, own fixed seed: AGREE x1, PARTLY x2 (the parity size is pinned to 1200x1200, other sizes rejected);
- open-pbr defaults as the material target: AGREE x1, PARTLY x2 (opacity and displacement defaults need a hashed read-back on an OCIO project; parameter names do not fix the lobe equations, which calibration decides);
- supporting the Tunic "Double sided" parameter by panel carve-out: DISAGREE x1, PARTLY x2 (the panel cannot widen 038; owner scope point);
- VIS-06 rewording: AGREE x1, PARTLY x2 (keep the exception-register clause, name the 256-sample pin and per-view variations).

## Decision

1. **Facade and native API.** The documented `substance_painter.display` symbols (environment, colour LUT, tone mapping, `ToneMappingFunction`, camera), the native `uzpainter.render.display` and `uzpainter.render.shader` calls and the MCP `display_*`, `shader_*` and `camera_*` tools stay, for script compatibility (CLR-03, OWN-04). Getters return the current state. A setter accepts a value the fixed pipeline uses (its pinned value, or a value the standard varies: the environment, the `ref_match` per-view rotation, the clear colour per preset, the camera) and rejects every other value with an explicit unsupported-value error naming the setting, the accepted values and decision 038; nothing is silently ignored (ARC-03). `set_color_lut_resource` accepts only no LUT. `get_tone_mapping` and `set_tone_mapping` raise `RuntimeError` on a colour-managed project, as Painter documents; on a Legacy project they raise the unsupported-configuration error. The capability manifest records each symbol's accepted value domain; a domain accepted only by the non-parity preview (for example an environment outside the standard) is marked non-parity.
2. **Display configuration.** The realtime preview and `painter_iray` implement one display transform: OCIO through OpenColorIO with Painter's substance config pinned by hash and the view `Default - sRGB`. Legacy `Linear`, Legacy `ACES`, ACE mode and every other OCIO view fail before rendering with an unsupported-configuration error citing decision 038. Legacy projects stay valid for texture work and export.
3. **Outputs.** `painter_iray` writes its parity artefact in the encoding of Save Render: a 16-bit RGBA display-referred PNG and a display-referred float32 EXR, at 1200x1200; any other size is rejected with the unsupported-value error. The RGBA32F linear accumulation may be written as an EXR labelled diagnostic and is never compared, because Painter has no linear output. UzPainter's own sampler keeps a fixed seed; Iray's seed is `uncontrolled` and the reference noise floor comes from the repeats.
4. **Material model.** The path tracer targets Painter 12.1.5's default `open-pbr` shader instance with its parameters at Painter's defaults. The old default-MDL parameters are replaced by the open-pbr parameters. Features that open-pbr leaves disabled by default (transmission, subsurface, coat, fuzz, thin-film, specular colour, anisotropy, diffuse roughness) are pinned off: they are not implemented, and a project whose shader enables one fails before rendering with an unsupported-configuration error. Height is applied as bump; displacement is pinned to the default instance's value and is not a variable. The lobe equations are chosen by black-box calibration, not inferred from parameter names. Opacity and displacement defaults are pinned only after the materials task has read the default shader's parameters back as hashed private evidence on an OCIO project.
5. **Non-default shader parameters.** Any non-default shader parameter value fails before rendering with the unsupported-configuration error. The Tunic v10 "Double sided" parameter is an owner scope point: the materials task verifies by hashed read-back whether it differs from the open-pbr default; if it does, the Tunic v10 production render stays out of Tier 3 acceptance until the owner amends decision 038 or the fixture.
6. **VIS-06.** The requirement stays MUST and reads "for the same state under the fixed render pipeline of decision 038", with the environment and render settings set by that pipeline and its per-view variations, Iray at min = max = 256 samples, and Iray's seed `uncontrolled` (decision 039); residuals still pass only through the exception register.

## Alternatives Considered

- Keep Legacy `Linear` and `ACES` for the non-parity preview only (rejected: a second display path for no parity gain, and the pipeline never creates Legacy projects)
- Remove the documented tone-mapping and colour-LUT symbols from the facade (rejected: CLR-03 requires the documented symbol set; scripts that guard on `RuntimeError` keep working)
- Support Tunic's "Double sided" by panel decision (rejected: the panel cannot widen decision 038; owner scope point)

## Consequences

Checklist items of the affected tasks are reworded, not deleted: an item made moot reads "pinned to <value> by decision 038". A change of the Assets3D standard, or a Painter build whose default shader or display transform differs, re-opens this scope. The owner decides whether Tunic v10's "Double sided" joins the supported scope.
