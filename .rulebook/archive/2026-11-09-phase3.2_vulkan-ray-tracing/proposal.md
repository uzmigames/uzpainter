# Proposal: phase3.2_vulkan-ray-tracing

## Why
VIS-06 and ARC-06 (`docs/prd.md`) require the clean-room path tracer to run on DX12 DXR and on Vulkan ray tracing, and the PRD §17 platform constraint (owner Q9, decision 022) makes Vulkan the second Windows backend. The vendored Vulkan backend has no acceleration structures and no ray queries: its RHI defaults return invalid handles and `SupportsRayTracing()` is false (`docs/architecture/13-engine-integration.md` §2.3). This child of P3-VULKAN (`phase3.3_vulkan-backend-ray-tracing`) adds Vulkan ray tracing as local modification UZP-MOD-007 (`13-…` §3.4), behind the same abstraction as DXR, implementing D12 and D6 (`13-…`, `07-preview-and-render-parity.md` §3.5).

## What Changes
- `thirdparty/uzengine-render-core/engine/rhi/vulkan/*` (UZP-MOD-007, logged in `MODIFICATIONS.md` with modification markers): `VK_KHR_acceleration_structure` with its required `VK_KHR_deferred_host_operations` behind the existing RHI BLAS/TLAS create and build calls; acceleration-structure descriptors; `VK_KHR_ray_query` with the `accelerationStructure` and `rayQuery` features enabled; `SupportsRayTracing()` reporting the real capability; descriptor-indexing bindless on Vulkan for the path tracer's material textures (`13-…` §2.3).
- Shader compilation: SPIR-V generated by DXC from the same HLSL with the `SPV_KHR_ray_query` extension when a kernel requests ray queries (UZP-MOD-006 path, `vulkan1.2` target).
- UzPainter-owned backend-neutral ray-query layer (`13-…` §4.1): capability query reporting inline ray queries per backend (DX12: DXR Tier 1.1 + SM 6.6; Vulkan: the three extensions and two features) with the list of missing items; the acceleration-structure builder for UzPainter's own meshes using the real vertex stride and a per-geometry opacity flag through the raw RHI `CreateBLAS` (never the vendored scene-level managers, `13-…` §2.4).
- Ray-cast fixtures under `parity/manifests/` (independently authored meshes and ray sets) and a compute kernel with inline ray queries, identical HLSL on both backends, that writes one hit record per ray; cross-backend comparison report under `parity/reports/phase3/` (numbers only).
- `selftest` ray-query qualification on Vulkan hardware next to the Phase 0 availability probe; `capabilities.json` entries for Vulkan ray queries.

## Dependencies
- Prerequisites: `phase3.1_vulkan-compute-parity` (Vulkan backend qualified for compute, readback and backend selection).
- Parent: `phase3.3_vulkan-backend-ray-tracing`. Its acceptance unblocks `phase3.7_path-tracer` (via the parent) and the optional `phase4.3_dxr-baker` `vulkan_rt` backend.

## Acceptance
Vulkan acceleration structures and inline ray queries work on the owner's GPU; the ray-cast fixtures run with the same kernels on DXR and Vulkan, every per-ray difference is reported, and any divergence passes only as an owner-approved exception in `parity/exceptions.json` (`docs/dag.md` P3-VULKAN; `07-…` §3.5). A missing feature reports unavailable with the missing items and never falls back.

## Impact
- Affected specs: vulkan
- Affected code: vendored Vulkan backend (UZP-MOD-007), shader compiler SPIR-V ray-query option, backend-neutral ray-query layer and acceleration-structure builder, ray-cast fixtures and comparison
- Breaking change: NO
- User benefit: the path tracer and the optional GPU baker can run on Vulkan as well as DX12
