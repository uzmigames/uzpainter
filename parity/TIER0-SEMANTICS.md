# Tier 0 semantics goldens

Task `phase0.6_tier0-semantics-goldens` (child of `phase0.8_tier0-goldens`, D3/D13). It records the goldens that settle the open compositing questions of `docs/architecture/04-layer-stack-and-compositing.md` §9 before the kernels are frozen. Painter is observed only through its documented Python API, driven by the recorder (`RECORDER.md`). Code: `tools/parity/tier0_semantics/`. Tests: `tests/parity/test_tier0_semantics.py` (corpus, coverage, store, guard) and `tests/parity/recorder/test_tier0_vocabulary.py` (recorder vocabulary). Manifests: `parity/manifests/tier0/semantics/<golden>.json` (golden id `tier0/semantics/<golden>`). Fixtures: `parity/fixtures/tier0-semantics/`.

The schema allows one golden per public manifest, so the task's public manifest is this folder of manifests. It replaces the single file `parity/manifests/phase0/tier0-semantics.json` named in the task spec.

## 1. Corpus

Every golden is one throwaway project, built by a UzmiGames instruction sequence and exported at 16 bit (PNG) or as 32-bit float (OpenEXR, for float channel formats). A golden that compares several configurations uses a grid mesh with one texture set per configuration (`s0`, `s1`, …), so one project carries a whole sweep. Value sweeps come from authored 16-bit bitmaps rather than from one uniform colour per golden. A 256×256 field gives every pair of 8-bit lattice values, and its blue channel holds every 16-bit code once.

| §9 item | Goldens (domain) | What varies |
|---|---|---|
| Blend formulas and spaces | `blend-basic`, `blend-additive`, `blend-contrast`, `blend-component` (`tier0/blend/modes`) | One `BlendingMode` per texture set: field B over field A on eight user channels (RGB16 at opacity 1 and 0.5, sRGB8 at 1 and 0.5, RGB8, RGB16F, L16 with the grey fields, RGB32F at 0.25) |
| | `blend-inputs` | Each input field alone, as stored (calibration of the sweeps) |
| | `blend-normal-channel` | `NormalMapCombine`, `NormalMapDetail` and `NormalMapInverseDetail` on the Normal channel, with authored tangent-space fields |
| | `blend-order` | Three non-commuting layers in four stack orders (04 §2) |
| | `colour-ramps-srgb`, `-working`, `-raw` (`tier0/colour/uniform-ramps`) | 288 uniform colours per documented colour space, each on an RGB16 and an sRGB8 channel (transfer-function fit) |
| Quantisation points | `quantisation-thirds` | Three fills at opacity 1/3 on one channel per `ChannelFormat` member, four colour triplets |
| Stack base values | `base-values-default`, `base-values-<template>` | An empty project with no template (plus one added channel per format), and one per shipped template (26) |
| Mask precision (8 vs 16 bit) | `mask-precision` | Mask fill effect with the bitmap that holds every 16-bit code; White/Black background, mask-effect opacity, two mask effects |
| Group `Normal`/`PassThrough` with masks | `group-masks` | Group in its default mode and in `Normal`, without and with masks on the group and on a child |
| Content-effect order | `effect-order` | Fill effect, levels and the starter-asset Blur filter in all six orders, plus single-effect controls |
| Levels clamp behaviour | `levels-clamp` | Input range inside (0.25–0.75) and beyond (−0.25–1.25) the ends, output −0.5–1.5, gamma, `clamp` off and on; float and 16-bit channels |
| The `BilinearHQ` kernel | `resample-uv` | UV projection of the 64×64 pattern and the 256 field at scales 1, 0.73, 1.37×2.11 and 3.3, rotation 30°, sub-texel offsets; `BilinearHQ`, `BilinearSharp` and `Nearest` |
| Height→normal methods and strength | `height-normal-plane-amplitudes`, `-sphere`, `-bevelled-cube` | The authored height ramps on three meshes, with the project's default method and strength. Amplitude is varied through layer opacity and a doubled height. `Normal_OpenGL`/`Normal_DirectX` virtual maps |
| The `AO_Mixed` operator | `ao-mixed` | The authored AO mesh map (ramp along x) against an AO channel ramp along y, at opacity 1 and 0.5, uniform, and empty |

API readback rules, the remaining §9 item, are recorded by `phase0.6_tier0-api-probes` (`RECORDER.md` §9). `corpus.COVERAGE` maps every other §9 item, worded as in the document, to its domains, and the coverage test reads §9 to check that every item is listed.

**Not reachable through the documented API.** The height→normal method and its strength are project or shader settings that the Python API (and the documented JavaScript API) can neither set nor read. The `PassThrough` group mode is listed in the python-doc but cannot be set on Painter 12.1.0. The owner moved them to the follow-up task `phase0.7_tier0-semantics-ui-cases` (answer to q1, 2026-10-10). That task records them through Painter's UI under decision 029. It is not a prerequisite of `phase0.8_tier0-goldens`, and until it closes the three cases are release gaps.

## 2. Fixtures

All fixtures are generated by `tools/parity/tier0_semantics/fixtures.py` (UzmiGames, Apache-2.0). The authored plane of the recorder sample, `parity/fixtures/meshes/plane.obj`, is reused.

| File | Content |
|---|---|
| `meshes/grid2x2.obj`, `grid4x2.obj`, `grid6x4.obj` | 4, 8 or 24 separate 10 cm quads, one material (texture set `s<i>`) each, full 0–1 UVs |
| `meshes/sphere.obj` | UV sphere, radius 10 cm, 32×16 segments, seam at u = 1 |
| `meshes/bevelled-cube.obj` | 20 cm cube with 2 cm rounded edges, 8×8 cells a face, one UV island a face in a 3×2 atlas |

| `bitmaps/grey-a.png`, `grey-b.png` | Grey16 ramps along x and along y (also the AO mesh map and AO channel) |
| `bitmaps/mask-codes.png` | Grey16 holding every 16-bit code once |
| `bitmaps/pattern64.png` | RGB16 64×64, deterministic pseudo-random codes |
| `bitmaps/height-ramps.png` | Grey16: a linear ramp, a cone, steps and a sine ridge, one per quadrant |
| `bitmaps/normal-a.png`, `normal-b.png` | RGB16 tangent-space normal fields |

## 3. Procedure

1. `python -m tools.parity.tier0_semantics write` regenerates the fixtures and manifests. It keeps existing `private_records` and refuses to change a manifest that already has records (goldens are immutable; a changed golden gets a new name). `check` compares the committed files with the generator, and the corpus test runs it.
2. Record each manifest under the shared Painter lock (`RECORDER.md`): `python -m tools.parity.recorder record parity/manifests/tier0/semantics/<golden>.json`. Each run holds `r1` (same session) and `r2` (after save and reopen).
3. Admit each run with `python -m tools.parity.store record <manifest> --run <inbox run>`, using the run whose record's `instruction_sequence_sha256` matches the manifest. Then run `python -m tools.parity.store verify parity/manifests/tier0/semantics`.
4. `python -m tools.parity.guard` must pass. Fits and stability are computed later from the stored records by `phase0.7_tier0-stability-fits`, and only fitted formulas are published under `parity/semantics/`.

The recorder vocabulary this corpus uses (groups, content and mask effects, levels, filters, UV projection, channel edits, effect sources) is listed in `RECORDER.md` §2.
