# Proposal: phase1.22_pyapi-cli-capabilities

## Why
Child of `phase1.24_python-api-facade` (P1-PYAPI in `docs/dag.md`), implementing D9 (decision 011) and D2 (decision 004, amended by decision 019) as specified in `docs/architecture/10-python-api.md` §1–§3, with the single-process role of D1 (decision 003) in `docs/architecture/02-runtime-topology.md` §1 and the CLI conventions of `docs/architecture/01-overview.md` §4. Scripts need a host: `UzPainter.exe run <script.py>` runs them in the worker role with the facade available, and is what the pipeline adapter calls in place of Painter's remote `execute_python`. Agents, gates and milestone names need to know exactly what works: the capability manifest generated by `phase1.2_docmodel-capability-manifest` must carry evidence-backed statuses for every Phase 1 symbol, be printable, and agree with what the API actually does, so nothing is silently a no-op. Requirements: INT-01, ARC-03, OWN-01, OWN-04 (`docs/prd.md`).

## What Changes
- `src/python/run.{h,cpp}`: `UzPainter.exe run <script.py> [args] [--gpu-backend dx12|vulkan]` hosting the worker role directly (02 §1; running a script file is the operator's explicit act, so no flag is needed); the script runs in the embedded interpreter with `uzpainter` and `substance_painter` importable; the value the script assigns to `result` is returned as JSON together with captured stdout and stderr; an uncaught exception is a structured failure carrying the traceback; output uses the prefixed JSON lines (`UZP_JSON:{...}`) and exit codes 0/1/2/3 of 01 §4, non-zero on failure (INT-01).
- `src/python/capabilities.{h,cpp}` and the CLI verb `uzpainter capabilities`: prints the shipped `capabilities.json`; `uzpainter.capabilities` exposes the manifest and `profile() == "painter-12.1-api-0.3.7"`.
- Phase 1 status population in the inputs of the generator (`tools/capabilities/`): each Phase 1 symbol and operation context of `uzpainter` and `substance_painter` marked `supported` only with Tier 0 evidence (set→get readback through a freshly resolved handle, persisted after save/reopen, golden comparison for output-affecting symbols) produced by the sibling tests and the `phase0.6_tier0-api-probes` goldens; symbols not yet implemented stay `release-gap`; desktop-only symbols stay `desktop-only-omitted` with their justification.
- Manifest-versus-behaviour conformance test (`tests/python/test_capability_conformance.py`): every `supported` entry is callable and cites existing evidence; every `desktop-only-omitted` entry raises `UnsupportedInUzPainter`; every `release-gap` entry raises `NotYetSupported` before mutation; every public facade or native symbol has a manifest entry.

## Dependencies
- Parent: `phase1.24_python-api-facade` (integration and acceptance of P1-PYAPI).
- Prerequisites: `phase1.3_document-model` (including `phase1.2_docmodel-capability-manifest`: generator, inventory, schema), `phase1.18_export-engine`, `phase1.8_project-store` (DAG inputs of P1-PYAPI) and the siblings `phase1.19_pyapi-native-module`, `phase1.20_pyapi-facade`, `phase1.21_pyapi-dispatcher-lifecycle` (their tests supply the Tier 0 evidence).
- Followed by the sibling `phase1.23_pyapi-pipeline-adapter`, which invokes `run`.

## Acceptance
- `run` returns `result`, stdout and stderr as JSON for a succeeding script and a structured failure with traceback and a non-zero exit code for a raising one.
- The regenerated `capabilities.json` validates, `uzpainter capabilities` prints it, and the conformance test passes: no `supported` entry without evidence, no symbol outside the manifest, no omitted or gap symbol that fails to raise.

## Impact
- Affected specs: `python-api` (`run` host, capability statuses)
- Affected code: `src/python/run.*`, `src/python/capabilities.*`, `tools/capabilities/` (status inputs), `tests/python/`
- Breaking change: NO
- User benefit: scripts run headless with a machine-readable result, and agents can trust the capability list
