## 2. The two crossings

### D12 — toolchain

In `03` I moved from Zig to "CMake/MSVC if the pinned commit builds green under the CMake mirror", for the CPython/MSVC CRT boundary. In `04` Astra moved the other way, with new source evidence: the CMake MSVC branch empties the job/ECS and DX12/DX11 source lists and excludes `shader_pipeline.cpp`, `rhi_factory.cpp`, `gpu_mesh.cpp` and `runtime.cpp` (`UZE\runtime\CMakeLists.txt` ≈119–139, 235–239, per `04` D12). My Phase 0 build test would therefore fail by construction, or build a library that lacks the renderer and jobs. **Settled: Zig-first.** The CRT/ABI concern that motivated my move is real but narrower than I stated: CPython's C API is C; the risk is CRT-object crossing and C++ exceptions across the module boundary. It becomes a Phase 0 qualification item (embed `python313.dll`, import the statically linked `uzpainter` module, round-trip 16-bit buffers, raise and catch across the boundary, import the vendored MCP SDK wheels) with a documented fallback: build the Python-facing layer as a separate DLL with a C ABI to the Zig-built core (the pattern UzEngine already uses for N-API, `UZE\docs\engine\06-build-toolchain\04-napi-bridge.md`). CMake remains a future option only if brought to functional parity. Not an owner question.

### D14 — pilot order

In `03` I moved tunic v10 ahead of belt v5 so the first pilot "counts"; in `04` Astra moved from tunic-first to my original wand → belt → tunic for fault isolation, keeping tunic recovery early and binding. **Settled: Wand v1 (smoke: import, binding, composition, export, save/reopen) → Belt v5 (production swatch/mask workflow, `base_tex`) → Tunic v10 (approved recovery: 22 fills, groups, `replace_height`, C07/F03 per-layer bindings, double-sided render state) — all three inside the first pilot phase, with tunic as the milestone that counts.** Both agree that none of the three covers native bake, proprietary materials, 3D generators or multi-set behaviour, so the locked bracers and historical hat v5 enter as early feasibility fixtures, hat v8 for current channel/export coverage and body v6b for multi-set stress.

Consequence for D13: **golden recording and recipe extraction use Painter's own Python API directly (remote scripting with our recorder scripts), never the bridge**, and any recipe captured through the bridge is re-validated against Painter before it becomes a fixture.
