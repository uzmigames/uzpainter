# Compact Project Container Format (Layer Stack + Masks + Cache)

Research compiled 2026-10-09. Corrected 2026-10-10 after the Astra technical review (`docs/analysis/reviews/technology-options-astra-review.md`); per-finding verdicts are in `05-review-response.md`. Web sources were retrieved 2026-10-10.

**Scope note (forwarded to architecture):** a container cannot be chosen before the authoritative project state is defined — versioned layer/effect graph, typed parameters, asset content hashes, seeds, source meshes/images, channel precision and color interpretation, sparse raster/stroke payloads — and before reproducible caches are separated from irreplaceable inputs. Flattened pixels alone do not preserve editable procedural behavior.

## Container Format Options

| Format | What It Is | Pros | Cons | License | Key Source |
|--------|-----------|------|------|---------|-----------|
| **HDF5 (Hierarchical Data Format 5)** | **Fact:** the three local Substance Painter projects checked start with the HDF5 signature `89 48 44 46 0d 0a 1a 0a` (checked 2026-10-09, re-checked 2026-10-10) at `E:\UzmiGames\Assets3D\Creatures\Undead\Skeletal Mage\Models3D\00-Corpo\`: 00-Corpo-v5.spp = 879,248,615 bytes, 00-Corpo-v6.spp = 1,087,438,533 bytes, 00-Corpo-v6b.spp = 1,190,431,812 bytes (single character body piece). This identifies these files as HDF5 containers ("HDF5" is the format family; the superblock version, library version and Painter's internal schema were not inspected, and other `.spp` variants were not checked). HDF5 stores typed n-dimensional datasets in a hierarchy of groups. | **Fact:** chunked datasets let chunks "be read and written individually", so a per-layer/per-channel/per-tile layout supports partial reads and writes. Compression filters require chunking; built-in filters include DEFLATE, SZIP, shuffle, Fletcher32 (checksum), N-bit and scale-offset; third-party filters (e.g., Zstd) can be registered or loaded as plugins. Typed arrays preserve integer/float precision; inspection tools exist (`h5dump`, `h5ls`). | **Real-world baseline:** 879,248,615–1,190,431,812 bytes per body piece for Painter's own schema and cache policy — a baseline for equivalent content, not evidence against HDF5 itself. **Hypothesis** (untested): size driven by baked geometry, caches, undo history or layer encoding; inspect dataset sizes, chunk layouts, filters, duplicates and free space read-only before attributing bloat. **Fact:** writing part of a compressed chunk reads the whole chunk through the filter pipeline, modifies it and rewrites it; rewrites can leave free-space holes (reclaimed with `h5repack`); chunk-cache tuning matters. Fletcher32 protects only datasets where it is configured; checksum detection is not an atomic commit. libhdf5 (and any Zstd filter) must be deployed or linked. The draft's "poor random access" and "rewrites structure on save" are rejected as inherent properties. | **Fact**: BSD-3-Clause. [Source](https://github.com/HDFGroup/hdf5/blob/develop/LICENSE) | [HDF5 chunking](https://support.hdfgroup.org/documentation/hdf5-docs/advanced_topics/chunking_in_hdf5.html); [filters](https://support.hdfgroup.org/documentation/hdf5/latest/_h5_z__u_g.html); [chunk issues](https://support.hdfgroup.org/documentation/hdf5/latest/hdf5_chunk_issues.html); local file check |
| **ZIP Container + JSON Manifest** | Single .zip containing: `manifest.json` (layer tree, UUIDs, properties), per-layer PNG/EXR files, bake cache as binary chunks, `metadata.json` (project settings, undo state checksum). Layers stored as `layers/<layer-uuid>.png`. Members may be stored (method 0), DEFLATE, or Zstandard (method 93). | Members are located through the central directory without decompressing other members (a compressed member must still be decoded; sub-regions inside a PNG are a separate issue); text manifest readable with standard tools; per-member CRC-32 detects many accidental errors. | **Fact:** libzip applies modifications on `zip_close()` by writing a temporary file and atomically replacing the original — "replace one file" still rewrites the archive file (whether unchanged members are copied without recompression is not confirmed in the inspected doc). An append-only incremental save needs a deliberate scheme: immutable generation names, a committed manifest/directory, recovery from incomplete tails, compaction. Duplicate member names are not portable across tools. CRC-32 detects but does not repair; a damaged central directory or manifest affects access to many members. The draft's "~4% directory overhead" is **unconfirmed**. | **Fact**: the ZIP APPNOTE (6.3.10, 2022-11-01) carries PKWARE usage terms — not public domain; library licenses (libzip, minizip) not re-verified here. [Source](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT) | [ZIP APPNOTE](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT); [libzip](https://libzip.org/documentation/libzip/) |
| **Zstandard-Compressed Archive** | ZIP or TAR wrapped in one outer Zstandard stream. `project.tar.zst` or `project.zip.zst` containing layers + manifest. | Lossless. The draft's "1–2× smaller than ZIP+DEFLATE" is **unconfirmed**. | A single outer frame has no member index: reading a member means decoding the stream up to it (not necessarily the whole archive). Independent frames with a seek table (zstd contrib seekable format) or per-member Zstd inside ZIP (method 93) give bounded access. Corruption impact depends on the frame layout, not automatically the whole project. | **Fact**: dual-licensed BSD **or** GPLv2. [Source](https://github.com/facebook/zstd) | [Zstandard GitHub](https://github.com/facebook/zstd); [seekable format](https://github.com/facebook/zstd/tree/dev/contrib/seekable_format) |
| **OpenRaster (.ora)** | Open specification for layered raster images (baseline v0.0.6): ZIP with `mimetype` first and stored uncompressed, `stack.xml` (layer stack), `data/` (layer PNGs), `Thumbnails/thumbnail.png`, `mergedimage.png`; only STORED and DEFLATED members are allowed. | Open spec; portable layer metadata (opacity, visibility, blend) in XML; useful raster interchange. | Not a PBR/procedural project format: no texture sets, material channels, bake cache or procedural state. The draft's blend-mode counts ("~20 vs 50+") are **unconfirmed**. | **Fact**: open specification. Application licenses previously listed (Krita, GIMP, MyPaint) are **unconfirmed**, are not format licenses, and GPL is not a permissive license. | [OpenRaster baseline spec](https://www.openraster.org/baseline/file-layout-spec.html) |
| **Custom Chunked Binary** | Single file of independently compressed typed tiles/blobs (e.g., per-chunk Zstd), an inspectable versioned manifest, stable IDs and content hashes, and an append-only committed index; constants and procedural parameters stored instead of materializing every full-resolution plane. Comparable ideas: USDZ 64-byte alignment, IFF/RIFF chunks. | Small incremental writes (append + new committed index), bounded per-layer/per-tile access, explicit corruption boundaries, deduplication across history, copy-on-write updates — **Hypotheses** until measured on real projects. Independent frames give bounded decode (zstd seekable format). | Own parser, specification, migrations and recovery tooling. Unknown chunks may be skipped only when declared optional (unknown authoritative effects cannot be ignored while claiming parity). mmap exposes encoded bytes, not decoded pixels. Resilience depends on the checksum and commit design — not inherently weaker than ZIP. Chunk size trades ratio against access latency and rewrite amplification. AI access needs a documented reader. | Project-defined; a custom format has no inherent license — record the licenses of libraries used (e.g., zstd BSD/GPLv2). | [Zstd seekable format](https://github.com/facebook/zstd/tree/dev/contrib/seekable_format); [USDZ spec](https://openusd.org/release/spec_usdz.html) |
| **USDZ (Universal Scene Description Zip)** | OpenUSD (Pixar) package — not a Khronos format: "a zero compression, unencrypted zip archive"; each file's data starts at a multiple of 64 bytes from the package start; allowed types include usda/usdc/usd, png/jpeg/exr/avif and m4a/mp3/wav. | Standard for USD scene interchange; contained images may use their own internal compression. | 3D-scene-centric; no standardized Painter-style layer/effect graph. No container-level compression (payloads can still be compressed). The draft's "~45%" ratio is withdrawn (no source). | **Not confirmed:** OpenUSD license name not re-verified in this pass (the draft's "Apache 2.0" is unverified). | [USDZ File Format Spec](https://openusd.org/release/spec_usdz.html) |
| **SQLite (whole project or index)** (added 2026-10-10) | Single-file transactional database holding the layer graph, assets, committed revisions, jobs and independently compressed tile BLOBs; or SQLite for metadata/indexing with external immutable blob files. | **Fact:** SQLite "is often used as the on-disk file format for desktop applications" (including CAD and media editing); transactions "appear to be atomic even if the transaction is interrupted by an operating system crash or power failure"; unlimited concurrent readers; SQL inspection with the `sqlite3` shell. | **Fact:** one writer at a time; in WAL mode committed changes sit in a `-wal` file (plus `-shm`) until checkpoint, and WAL does not work over network filesystems — a portable single-file snapshot needs a checkpoint/backup step. No built-in BLOB compression. External blob files are outside the transaction (needs publish ordering, integrity validation and orphan collection). Page/journal overhead unmeasured. | **Fact**: public domain. [Source](https://sqlite.org/copyright.html) | [Appropriate uses](https://sqlite.org/whentouse.html); [atomic commit](https://sqlite.org/atomiccommit.html); [WAL](https://sqlite.org/wal.html) |

## Comparison: Random Access, Incremental Save, Compression, Resilience

| Capability | ZIP+JSON | Zstd TAR | OpenRaster | Custom Binary | USDZ | Chunked HDF5 | SQLite |
|------------|----------|---------|-----------|-----------------|------|------|------|
| **Random access to one layer** | Yes (central directory; member still decoded) | Sequential decode up to the member (single frame); bounded with seekable/indexed frames | Yes (ZIP) | Yes (offset/index table) | Yes (ZIP; uncompressed members) | Yes (per chunk) | Yes (row/BLOB) |
| **Incremental save** | Logical edit yes; libzip rewrites the archive (temp file + atomic replace); append scheme possible by design | No (re-archive) | As ZIP | Append + new committed index (by design) | As ZIP (64-byte alignment kept) | Per-chunk writes; compressed chunks read-modify-write; free-space holes | Transactional page updates |
| **Compression ratio** | **Unconfirmed** — per-member stored/DEFLATE/Zstd | **Unconfirmed** | **Unconfirmed** — STORED/DEFLATED only | **Unconfirmed** — per-chunk codec | No container compression (payloads may be compressed) | **Unconfirmed** — per-chunk filters | No built-in BLOB compression |
| **Corruption resilience** | CRC-32 per member detects, does not repair; directory/manifest damage affects many members | Layout-dependent | As ZIP | Depends on checksum and commit design | As ZIP | Optional Fletcher32 per dataset; no atomic commit | Atomic transactions (journal/WAL) |
| **Tool inspection** | unzip + text/image tools | zstd + tar | unzip, XML | Own diagnostic reader required | unzip, USD tools | h5dump, h5ls | sqlite3 shell |
| **AI readability** | Needs a documented schema and reader/MCP resource in every case; text storage alone is not sufficient and binary storage is not a blocker | Same | Same | Same | Same | Same | Same |

All draft compression percentages (~40%, ~25–35%, ~20–30%, ~45%) are withdrawn: no source or measurement supports them; payload entropy dominates container ratios.

## Trade-Off Summary

**Recommendation for UzPainter Save Format (revised 2026-10-10):**

1. **No container is selected yet (decision reopened; forwarded to architecture)**:
   - **Why**: the draft's choice rested on unsupported claims (trivial ZIP incremental save, HDF5 random-access limits, size ratios). Retain lossless authoritative project data; benchmark a ZIP + manifest baseline against chunked HDF5 with a documented UzPainter schema, SQLite, and a custom indexed chunk container on the same representative projects, including the three `.spp` baselines with equivalent retained inputs and history.
   - **Every candidate must provide** (Recommendation): an `inspect_project` reader/MCP resource with schema/version reporting, layer/channel enumeration, hashes, dependency provenance and selective preview/plane extraction, plus an independently readable specification.
   - **Baseline structure** (ZIP candidate), `project.uzp`:
     ```
     manifest.json          # { layers: [...], metadata: {...}, version: "1.0" }
     bake_cache.bin        # Monolithic bake state (or per-layer chunks)
     layers/
       uuid-1.png          # sRGB or linear, lossless
       uuid-2.png
     metadata.json         # Undo checkpoint markers, project settings
     ```
     PNG per layer covers only 8/16-bit integer raster planes. A layer's multiple material channels, masks, generators, filters, strokes, fill projections, dependencies, texture sets and UV tiles need explicit schema definitions; float data needs lossless EXR or raw typed tiles.
   - **File size**: the draft's "~30–50 MB / ~10–20 MB for a typical 4K project" is **unconfirmed** and withdrawn.

2. **Alternative (Zstandard wrapper for external distribution)**:
   - An outer `project.uzp.zst` loses bounded member access; the draft's "~20–30% reduction" is **unconfirmed**. Prefer per-member (ZIP method 93) or per-chunk Zstd if Zstd is used.

3. **Re-evaluated (previously "Avoid")**:
   - **HDF5**: no longer excluded. The `.spp` sizes reflect Painter's data model and cache policy, not an inherent HDF5 cost; keep chunked HDF5 in the benchmark.
   - **Custom Binary**: in the benchmark; maintenance burden is real; AI access comes from an exposed reader, as for any binary format.
   - **USDZ**: 3D scene package; no container compression (payloads may be compressed); not a project container.
   - **OpenRaster**: raster interchange only (no material channels, bake cache or procedural state).

**Undo/History Strategy:**
- Store linear checkpoint chain: `undo/checkpoint-0.json`, `undo/checkpoint-1.json`, etc., each referencing layer state at that step.
- Alternatively: delta encoding (only changed layers per checkpoint); complex but compact.
- **Correction:** ZIP does not make this append-only by itself; it needs a deliberate append/commit scheme (see ZIP row), and libzip's normal modification path rewrites the archive. Undo/history needs retained references and retention rules; it is not disposable cache.

**Bake Cache Storage:**
- Bake results (Normal, Height, Curvature from geometry import) stored in binary chunks, indexed by UUID in manifest.
- A bake cache is regenerable (and may be dropped) only while its source mesh, settings and an equivalent deterministic baker of the same version remain available; otherwise it must be retained. Policy forwarded to architecture.
