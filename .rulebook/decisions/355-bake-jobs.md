# 355. Bake jobs: one native job per launch bakes every set and publishes them in one transaction; Python's bake_async and MCP bake_start start it with every refusal before any event, and decision 001 refuses each pending-evidence usage at the publication

**Status**: accepted
**Date**: 2026-10-22
**Related Tasks**: phase3.3_baker-evidence-publication, phase3.5_embree-bakers

## Context

Items 2.5-2.7 of phase3.3_baker-evidence-publication add asynchronous execution to decision 347's CPU baker and publication. The interfaces are `06-baking.md` §6, Python's `baking.bake_async`, `bake_selected_textures_async`, `BakingStatus`, `BakingProcess*`, `project.is_busy`, `async_utils.StopSource`, and the ledger-backed MCP `bake_start`. Approved source A-PYDOC describes a launch with the selected baking settings that returns `StopSource` without waiting for completion. `BakingProcessAboutToStart(stop_source)` exposes a comparable cancellation handle. `BakingProcessProgress(progress)` carries a fraction from zero to one; `BakingProcessEnded(status: BakingStatus)` distinguishes `Success`, operator cancellation (`Cancel`) and an error (`Fail`, diagnosed in the log). Baking makes `is_busy()` true. The documentation leaves two details unspecified: where `BusyStatusChanged` falls relative to the start event, and how cancellation behaves after completion. No Tier 0 bake capture exists yet.

The forks: what one job covers when several sets bake, where refusals happen, how decision 001 applies to a bake whose every usage is `pending-evidence`, and the event order Painter does not document.

No model panel ran: the coordinator fixed the scope (items 2.5-2.7, 3.3-3.6, CPU and Embree only) and the rule for parity (pending-evidence usages stay refused at publication, checked through the receipt's `parity_status`); each fork below follows that rule, the python-doc or an existing UzPainter contract.

## Decision

1. **One job, one commit point** (`src/bake/job.h`). `BakeJob::Start` asks the baker for every set's job at once, so each refusal of every set is raised before any work. The job's progress is the mean of the sets' tile fractions; `cancel()` is acknowledged at once and checked at tile boundaries. After every set baked, the publisher runs once and binds every set in one transaction, or nothing (`PublishInto`, decision 347's checks, for each set). A stop before the commit point ends in `Cancel`, `before_publication`; a stop that arrives while the publication runs or after it committed ends in `Cancel`, `after_publication`, the bindings intact; a stop after the end is refused. One `BakerDetail` per (set, usage) says `published`, `failed`, `refused`, `not_published` or `cancelled`, with the error. A test seam (`BakeJobOptions::fail_usage`) fails one usage's baker after the cast.
2. **Inputs from the project** (`src/bake/job_inputs.h`). The low parts are the stored mesh re-derived (`RederiveMesh`) and split by the set's material; the high and cage meshes are the files `HipolyMesh` and `CageMesh` name (as `bake_set_mesh_inputs` stores them); every other setting is `RequestFromParameters`'s; the Normal convention is the project's. The usages are the caller's or the set's enabled bakers. Refused before any work: a usage no binding can hold (`PublishedFormat`; the default configuration's Curvature, ID, Position, Thickness and WorldSpaceNormal), and CageMode Automatic (`NotYetSupported`, the inventory's release-gap context, which the baker refused with a capability error).
3. **Decision 001 at the publication** (`src/bake/job_session.h`). The session's publisher builds each set's receipt and refuses every usage whose receipt `parity_status` is not `supported`, naming the receipt hash and the owner task, before any change. Today every usage is `pending-evidence`: a session bake bakes, fails with each baker `refused`, and binds nothing; the job's error carries the report. A supported usage would publish through the call's own mutation request (Python's `Mutate`, MCP's admitted request), so the ledger resolves it from the operation rows.
4. **Python** (`uzpainter.baking.bake_async(texture_set_name, usages=None)`, `bake_selected_textures_async(usages=None)`). They start the session bake on the native job pool (kind `bake`, run even while engine computations are paused) and return its `jobs.Job`; `BusyError` while another job runs. The facade's `bake_async(texture_set)` and `bake_selected_textures_async()` are Painter's: the native call raises every refusal before any event; then, during the call, `BakingProcessAboutToStart(stop_source)` is delivered and the busy section entered (`BusyStatusChanged(True)`), so `is_busy()` is true when the call returns; a follower thread delivers `BakingProcessProgress` at each change of the job's progress, then `BakingProcessEnded(status)` and `BusyStatusChanged(False)`, all on the dispatcher thread. `request_stop()` cancels the job and returns False once the job ended. A `Fail` logs its cause (Painter: "detailed in the log"). `uzpainter_facade.baking.start(texture_set, usages)` is the launch both use; tests reach a bakeable usage through it, since no call stores the enabled bakers yet (decision 323).
5. **The unrecorded order.** `BakingProcessAboutToStart` before `BusyStatusChanged(True)` and `BakingProcessEnded` before `BusyStatusChanged(False)` follow the recorded export (`ExportTexturesAboutToStart` not busy, `ExportTexturesEnded` busy; R10, decision 319). Every symbol stays `pending-evidence` until the bake probe records Painter's order (decision 297; phase3.5_embree-bakers). `BakingStatus` member values (0, 1, 2) are not documented and no output depends on them.
6. **MCP `bake_start {sets?, usages?, wait?}`** is a long job tool with commit point `revision`: refusals are `capability_gap` or `invalid_arguments` before any job; `job_cancel` cancels the bake at once (`cancelled`, `stopped: before_commit`); a worker killed during a bake leaves the job `interrupted`, resolved from the operation rows. `usages` is UzPainter's: Painter's API has no such argument, and the default configuration's bakers are refused.

## Alternatives Considered

- **One transaction per set.** Rejected: a later set's bake read the revision the first set's publication replaced, so the strict revision check of decision 347 would refuse it, and a cancel between sets would leave a partial job.
- **Refusing every pending-evidence usage before the cast.** Not taken: the coordinator's rule checks parity through the receipt, and the bake then yields its receipt for the evidence.
- **Raising from `bake_async` for a refusal found after the cast.** Rejected: the call has returned; Painter documents `Fail` with the cause in the log.

## Consequences

- New: `src/bake/job.{h,cpp}`, `job_inputs.{h,cpp}`, `job_session.{h,cpp}`; `tests/bake/job_bake_cases.h` (four native cases); `tests/supervisor/test_supervisor_bake.py`; a facade test in `tests/python/test_pyapi_baking.py`.
- Changed: `bake_publication.{h,cpp}` (`PublishInto`, `PublishBake` over it), `build.zig` (the baker and the job in `UzPainter.exe` and `uzp-pyapi-tests.exe`, Embree beside the pyapi runner), `bind_baking.cpp`, `bind_misc.cpp`, the facade's `baking.py` and `event.py`, `substance_painter/baking.py`, `typed_tools.cpp` (`bake_start` is a job tool).
- Capabilities: `substance_painter.baking.bake_async`, `bake_selected_textures_async`, `BakingStatus` (and its members), `uzpainter.baking.bake_async` and `bake_selected_textures_async` go from `release-gap` to `pending-evidence`; `event.BakingProcessEnded.status` stays as listed (a dataclass field, not a class attribute: absent like every event field); the bake's three release-gap contexts stay gaps; the MCP operation `bake.start` is available.
- Open: publication through Python and MCP waits for Tier 2b parity of a usage; a successful session bake (`Success`) and a publication committed before a cancel are covered natively only.
