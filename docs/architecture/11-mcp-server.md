# 11 — MCP server

Implements D10 (`05-resolution.md`) as answered by the owner on 2026-10-10 (Q12: `run_python` is a trusted opt-in behind `--allow-python`, and every required operation is reachable through typed MCP tools). Requirements: INT-01…07, LAY-06, LAY-07, QG-03, ARC-01, ARC-02, ARC-14 (`docs/prd.md`). Protocol facts: `docs/analysis/technology-options/04-mcp-server-options.md` and `05-review-response.md` (revision 2026-07-28; the official Python SDK v2 has no Tasks support; the client launches a stdio server and owns its pipes).

## 1. Topology

The supervisor (`02-runtime-topology.md`) hosts the official Python MCP SDK (pinned release, vendored) in its embedded interpreter. Transports: **stdio** (default; stdout carries protocol frames only, logs go to stderr and to the ledger) and **Streamable HTTP** on `127.0.0.1:<port>` when started with `--mcp-http` for a resident instance (Origin validation, bearer token generated at start or given by `--token`; never bound to a non-loopback address without `--allow-remote`). Both transports call the same tool registry; tool handlers forward to the worker over the private pipe and run in an executor so the event loop keeps serving progress and cancellation.

## 2. Tools

Compact, task-shaped tools for the operations the pipeline performs, plus typed operation families so every required operation is reachable without Python (owner Q12). A **requirement-to-typed-operation matrix**, generated with the capability manifest and published as part of `uzpainter://capabilities`, maps every required operation (PRD INT-02, ARC-14 and the requirements each family serves) to its tool and its conformance fixture; a required operation without a typed tool is a release gap, never a reason to depend on `run_python`. Brush strokes are out of scope (owner Q5), so there is no stroke tool. Every mutating tool accepts `idempotency_key` and `expected_revision`; every result carries `revision`, `committed_revision`, `job_id` where applicable, `changed/created/hidden/imported/skipped` lists and `warnings`.

Schemas carry numeric bounds, enums and object references; the server validates inputs before admission (not only by description). A property may name the capability-manifest operations each of its values needs (`x-uzpainter-capability`), so a value whose family is a release gap (a paint layer, a triplanar projection) fails `capability_gap` before admission while the tool's other values work (decision 164). The worker serves the typed families (`src/supervisor/typed_tools.cpp`, one transaction per mutating call over the edits the `uzpainter` API runs); `status`, `capabilities`, `batch`, the resources and the prompts are the supervisor's (decision 165). Results are `structuredContent` plus a short text summary. Images are returned as content blocks only for `capture`; everything else references files under the allowlisted roots.

## 3. Long jobs

`bake_start`, `export`, `capture`, `mesh_reload`, `project_create/open` return `{job_id, status}` immediately, or block with `wait=true` while emitting progress notifications. Clients poll `job_status`/`job_result` or wait. Terminal states are durable in the supervisor ledger (`succeeded | failed | cancelled | interrupted`). `job_cancel` acknowledges intent; the final receipt says whether work stopped before or after commit. The MCP Tasks extension is added behind the same job ledger when a pinned SDK release and the owner's clients support it; `job_*` tools remain.

## 4. Single writer, revisions, retries

- One mutation **lease per open project**: `lease_acquire {owner}` is implicit for a stdio client (the only client) and explicit in HTTP mode; a mutating call without the lease returns `lease_held {holder, since, active_job}`. Reads use committed snapshots and need no lease.
- **Revision precondition.** Each mutation carries an original base revision (`expected_revision`) captured before its first admission and preserved with its `idempotency_key` on every retry. The native IPC requires that precondition (`02-runtime-topology.md` §2); a public wrapper that permits omission resolves it once before submission and preserves it for retries. At the MCP boundary a call may omit `expected_revision` only when it also omits `idempotency_key`: the supervisor then generates the key, resolves the precondition once before submission, records both in its ledger and returns both in every receipt for retries. A client that supplies its own key supplies its original `expected_revision` with it on every attempt.
- **Idempotency is bound to the persisted revision.** Each mutating transaction writes the operation record `{project_uuid, idempotency_key, request_hash, outcome, committed_revision}` into the project store in the same SQLite transaction as its revision (`09-project-file-format.md`); `request_hash` is the SHA-256 of the canonical JSON of the tool name and its arguments. A key is scoped to its project UUID (`project_create` writes the record into the new project's first transaction; `project_save_as` commits no revision, so it is a long lifecycle call that a repeat answers by saving the same revision to the same file, decision 164). A record is retained as long as its revision is retained (owner Q11: current and previous checkpoints plus the last 50 mutation revisions); within that window a known-key retry returns its recorded outcome; outside it the unknown-key rule below applies.
- A known key and its `request_hash` are checked before the current revision: replaying a key with the same `request_hash` returns the recorded outcome even when the current revision is newer, never a second mutation; reusing a key with different arguments returns `idempotency_conflict {key, committed_revision}`.
- After a worker restart the supervisor reconciles its ledger from the operation records of the open project before it admits any mutation. A key found in the records returns its recorded outcome. An unknown key with a missing or expired original precondition returns `outcome_unknown {committed_revision}` and is never executed. An unknown key with an unexpired precondition may execute only if that precondition still equals the current revision; otherwise it returns `stale_revision {expected, current}`. The pruning horizon (`meta.operation_horizon_revision`, `09-project-file-format.md` §4) identifies the range for which operation-history completeness is guaranteed; a precondition below it is expired. If the records cannot be read, the call fails with `outcome_unknown {committed_revision}` and is never run as a new mutation. Absence from the supervisor ledger never proves that a mutation did not commit; the ledger is a control-plane record, not a second editable document.
- A call while a conflicting job runs returns `busy {job_id}` rather than queueing silently (INT-05); `wait_idle {timeout}` exists for scripts, and a timeout is a failure, not a continuation.

## 5. Path roots

`--roots project=<dir>;mesh=<dir>;bake_mesh=<dir>;resource=<dir>;export=<dir>` (the Assets3D client sets all five to `E:\UzmiGames\Assets3D` today — `A3D\Pipeline\mcp\painter_mcp_client.py`). Paths are canonicalised (absolute, resolved reparse points, `file:///` and relative forms normalised) and checked against the root of the operation; results never reference paths outside the roots. Roots are policy for structured tools; they do not sandbox `run_python` (Q12).

## 6. `run_python`

Registered only when the supervisor starts with `--allow-python` (owner Q12); executes in the worker interpreter with the full `uzpainter` and `substance_painter` APIs; returns `result`, stdout and stderr separately; honours the lease and revision rules like any tool. Each API call inside the script is its own transaction (`10-python-api.md` §5): a script that raises after earlier calls keeps those calls committed, and its error receipt reports the last committed revision and the partial changes; atomic multi-call work uses the native `Transaction`. It is trusted execution for the local operator, documented as such. Typed tools cover every required operation, so a deployment runs without it: the requirement-to-typed-operation matrix is maintained from Phase 2, the Python-disabled Belt round is the integration evidence of P2-BELT for G2, and release (P5-REPORT/G5) requires every matrix row to pass with a Python-disabled conformance fixture for every required operation family (§7).

## 7. Settling evidence by milestone

Each check runs with the package that owns it and its predecessors; later integration evidence is attached to the later gate. The complete requirement-to-typed-operation matrix (§2) is maintained from Phase 2, and all of its rows must pass at release.

- **Phase 2, P2-MCP.** Typed-tool, transport, lease, error and retry contract fixtures pass on synthetic project/job fixtures: two writers, a lost acknowledgement with retry, a worker killed immediately after the durable project commit and before the supervisor's acknowledgement (retry the same request, then a changed request with the same key), reconnect in HTTP mode, a path outside the roots, and a stale revision. Commit a non-idempotent mutation, advance beyond retention and compact, lose the supervisor ledger, then replay the original key with its original precondition and with no precondition: neither replay may create another mutation; a known-key replay inside the window still returns the stored result despite a newer current revision. Operation families whose implementation is not yet available are reported as capability gaps, and the capability resource shows any operation that still needs Python as a gap.
- **P2-BELT / G2.** Complete the belt round through MCP only, with `--allow-python` off (integration smoke test).
- **P3-BAKER.** Cancellation during a native bake; the final receipt says whether work stopped before or after commit (§3).
- **P5-REPORT / G5.** Full Python-disabled conformance for every required operation family in the matrix, after its implementation is available: project lifecycle, texture sets, resources, the stack family including the later node, effect and source kinds and paint layers receiving bitmaps and projections, recipes (`sync_stack` name addressing and group-only rebuild, LAY-06/07), native bake, mesh reload, every export target, capture in each mode, diagnostics, and jobs/lease.
