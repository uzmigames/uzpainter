# Python Embedding and Packaging for Windows .exe

Research compiled 2026-10-09. Corrected 2026-10-10 after the Astra technical review (`docs/analysis/reviews/technology-options-astra-review.md`); per-finding verdicts are in `05-review-response.md`. Web sources were retrieved 2026-10-10.

**Fact:** The options below are not mutually exclusive. They sit on independent axes: (1) interpreter runtime and its distribution (CPython from the Windows embeddable ZIP or a custom build); (2) how C++ talks to the interpreter (raw C API, pybind11 helpers, nanobind extension bindings); (3) process model (in-process interpreter vs. Python worker process); (4) delivery form (folder with a native entry point vs. a self-extracting single file such as PyInstaller `--onefile`). pybind11 and nanobind both require CPython; PyInstaller freezes a Python-led application. [CPython embedding guide](https://docs.python.org/3/extending/embedding.html); [Windows embeddable package](https://docs.python.org/3.13/using/windows.html#the-embeddable-package).

## Trade-Off Summary

**Packaging Strategy:**
- **Native entry point + private runtime folder:** `UzPainter.exe` (C++) loads the bundled `python3XX.dll` extracted from the embeddable package and exposes an `uzpainter` module (C API, optionally pybind11). **Fact:** Python's Windows docs describe this ("directly use `python3.dll`"; extracting the distribution to a subdirectory "is sufficient to provide a loadable Python interpreter"). No `python.exe` or batch file is visible to users. Dependencies are vendored at packaging time; the Microsoft C Runtime must be provided by the installer.
- **Single self-extracting file:** PyInstaller `--onefile` (Python-led apps only) unpacks to a temporary folder at each launch and starts "a little slower" than one-folder mode; no startup figure is documented.
- **One executable with no adjacent or extracted runtime files:** requires a custom static CPython build and static registration of every extension module — a separate integration project not established by any source cited here. The official Windows package ships DLLs; adding pybind11 does not change that.
- All footprint ranges in the 2026-10-09 draft (~30–50 MB, ~70–120 MB, ~20–40 MB) are withdrawn as **unconfirmed**. Measure compressed download, installed files and startup for the same dependency inventory under each candidate.

**Python API Exposure (for UzPainter scripting):**
- **In-process, C++ calling Python:** embed CPython (C API, optionally pybind11); Python plugins import a module (e.g., `uzpainter.*`) exposed by the C++ core. No IPC. A Python exception is reported to the caller through the C API and is not by itself a process crash; native faults in extension code share the host's failure domain (own knowledge, high confidence).
- **Out-of-process, subprocess:** bundle Python and run it as a child; communicate via pipes or sockets. Isolates interpreter and extension faults from the renderer, but the worker cannot access the parent's C++ objects directly; all state crosses an IPC boundary (copy/serialization cost not measured). A Python client library driving a native process is a further option if in-process plugins are not required.

**GIL and Concurrency (for long bakes):**
- **Fact:** Conventional CPython does not block native C++ threads that do not hold the GIL. Binding code can release the GIL around long native calls (`Py_BEGIN_ALLOW_THREADS` in the C API; explicit release in pybind11/nanobind) or enqueue work on the C++ job scheduler. [CPython C API: threads](https://docs.python.org/3.13/c-api/init.html)
- **Fact:** Free threading (PEP 703) in Python 3.13 is a separate interpreter build (`./configure --disable-gil`; `sysconfig` variable `Py_GIL_DISABLED`), not a PyInstaller or pybind11 compile flag (the draft's `Py_NOGIL` was wrong). Importing an extension not marked free-threading-compatible re-enables the GIL; `PYTHON_GIL=1` or `-X gil` also re-enable it. [Free-threading HOWTO](https://docs.python.org/3.13/howto/free-threading-python.html)
- **Fact:** CPython 3.12+ can create a sub-interpreter with its own GIL via `Py_NewInterpreterFromConfig()` and `PyInterpreterConfig_OWN_GIL`; the default is the shared GIL, and isolation (no shared objects or mutable state) is the caller's responsibility. pybind11's support for this arrived in 3.0.0 (2025-07-10), not 2.13.0. [CPython C API](https://docs.python.org/3.13/c-api/init.html); [pybind11 changelog](https://pybind11.readthedocs.io/en/stable/changelog.html)
- **Recommendation:** start with a pinned conventional interpreter and native job dispatch; justify free threading or isolated sub-interpreters only with a measured Python-side workload.

**Hypothesis to Confirm in Next Phase:**
- Painter's interpreter location and whether it runs in-process remain **unconfirmed**; this is not needed to choose UzPainter's design.
- PyInstaller one-file startup overhead for UzPainter's dependency set is unmeasured.

**Recommendation Route:**
1. **Recommendation:** native `UzPainter.exe` + private CPython runtime from the embeddable package, initialized through the C API (`PyConfig`), with pybind11 added where its helpers reduce code; vendor a pinned, tested dependency set.
2. **Recommendation:** PyInstaller only if a Python-led launcher is acceptable; free threading is a separate interpreter-build decision, not a PyInstaller option.
3. **Fact:** nanobind is not an embedding API; it remains a possible extension-binding choice combined with direct C API embedding (**Hypothesis**, see table).
